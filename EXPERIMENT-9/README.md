# DBMS Experiment 9 – Railway Booking Database: Indexing and Query Optimization

## Aim

To create a Railway Booking table containing at least 5,000 records, execute SQL queries before and after creating indexes, and compare query execution plans using the `EXPLAIN` command.

## Overview

This experiment demonstrates database indexing and query optimization using a Railway Booking Management System.

A railway booking database is created with 5,000 records using a Recursive Common Table Expression (CTE). Different SQL queries are executed before and after creating indexes to understand how indexing affects query execution.

The `EXPLAIN` command is used to inspect query execution plans and understand how MySQL accesses data.

## Technologies Used

- **Database:** MySQL
- **Language:** SQL
- **Storage Engine:** MySQL InnoDB
- **Concepts:** Indexing, Query Optimization, EXPLAIN, Recursive CTE, Aggregate Functions, Composite Indexing

## Sample Data Generation

The experiment generates 5,000 railway booking records using a Recursive CTE.

```sql
WITH RECURSIVE Numbers AS (
    SELECT 1 AS n
    UNION ALL
    SELECT n + 1
    FROM Numbers
    WHERE n < 5000
)
```

The generated records contain passenger details, train information, stations, journey dates, seat numbers, booking statuses, and fares.

### 1. Table Creation

### 5. EXPLAIN Command

The `EXPLAIN` command displays the execution plan used by MySQL to execute a query.

It helps analyze:

- Table access methods.
- Possible indexes.
- Selected indexes.
- Estimated rows examined.
- Filtering efficiency.

Example:

```sql
EXPLAIN
SELECT *
FROM Railway_Booking
WHERE Train_No = 12005;
```

### Composite Index

The experiment also creates a composite index:

```sql
CREATE INDEX idx_train_date
ON Railway_Booking(Train_No, Journey_Date);
```

This index is designed to support queries that filter using both Train Number and Journey Date.

## Before and After Indexing

The experiment compares query execution plans before and after creating indexes.

| Before Indexing | After Indexing |
|---|---|
| Queries may require full table scans | Queries may use available indexes |
| More rows may need to be examined | Fewer rows may need to be examined |
| No additional secondary indexes | Multiple secondary indexes available |
| Query execution plans are inspected using EXPLAIN | Query execution plans are inspected again using EXPLAIN |

**Note:** Indexes do not guarantee that every query will become faster. MySQL's query optimizer decides whether an index should be used based on its estimated cost, selectivity, and available statistics. Low-cardinality columns such as Booking_Status may not always benefit from an index.
